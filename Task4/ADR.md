## Часть 1. Сравнение контекстных решений (C1)

### Критерии

| № | Критерий          | Описание                                                |
|---|-------------------|---------------------------------------------------------|
| 1 | Автономность      | Работа фермы без интернета ≥24 часов                    |
| 2 | Время оповещения  | От нештатной ситуации до оповещения оператора <5 секунд |
| 3 | Затраты на ферму  | Оборудование на одной ферме                             |
| 4 | Масштабируемость  | Создание новых ферм                                     |

### Анализ

| Критерий         | Автономная ферма (Локальный диспетчер)   | IoT-шлюз (всё в офисе)                                         |
|------------------|------------------------------------------|----------------------------------------------------------------|
| Автономность     | Полная (24+ часов)                       | Нет (зависит от интернета)                                     |
| Время оповещения | <5 секунд                                | >5 секунд (зависит от связи)                                   |
| Затраты на ферму | Высокие (GPU-сервер)                     | Низкие (только шлюз)                                           |
| Масштабируемость | Высокая (фермы независимы)               | Низкая (центральный сервер принимает все данные — узкое место) |

**Вывод по C1:** выбираем автономную ферму — соответствует функциональным и нефункциональным требованиям ТЗ. Решение с IoT-шлюзом нарушает критические из них.

## Часть 2. Сравнение контейнерных решений (C2)

### Критерии

| № | Критерий                  | Описание                       |
|---|---------------------------|--------------------------------|
| 1 | Сложность реализации      | Трудозатраты на разработку     |
| 2 | Сложность поддержки       | Администрирование, отладка     |
| 3 | Надёжность                | Количество узких мест          |
| 4 | Расширяемость             | Добавление новых сервисов      |
| 5 | Задержка передачи событий | Время между сервисами          |

### Анализ

| Критерий                  | Без брокера (с локальной БД)            | С брокером (RabbitMQ)                           |
|---------------------------|-----------------------------------------|-------------------------------------------------|
| Сложность реализации      | Средняя                                 | Выше среднего (дополнительный инфра-компонент)  |
| Сложность поддержки       | Низкая                                  | Средняя (очереди, права, мониторинг)            |
| Надёжность                | 1 узкое место (БД без репликации)       | 1 узкое место (RabbitMQ с ограниченной памятью) |
| Расширяемость             | Средняя (новый сервис = правка вызовов) | Низкая (новый сервис = подписка на очередь)     |
| Задержка передачи событий | Низкая (прямой вызов)                   | Средняя (через брокер)                          |

**Вывод по C2:** для MVP выбираем решение без брокера — проще при небольшом числе сервисов. При росте числа сервисов на ферме (10+) возможно перейти на RabbitMQ.

---

## Итоговая рекомендация

**Выбрана архитектура:**
- Уровень C1: автономная ферма (Локальный диспетчер)
- Уровень C2: без брокера (прямые вызовы + TimescaleDB)

**Обоснование:** соответствует требованиям автономности и времени оповещения, минимальная сложность для MVP, снижение затрат на разработку и поддержку. При масштабировании предусмотрен переход на RabbitMQ.
