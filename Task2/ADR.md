# ADR №2: Контейнерная архитектура (C2) платформы мониторинга свиноводческих ферм

## Ссылка на ADR №1
[ADR №1](../Task1/ADR.md)

## Контекст
ADR №1 определил контекстную архитектуру (C1) и стратегию: на каждой ферме разворачивается Локальный диспетчер для автономной работы. Настоящий документ уточняет архитектуру до уровня контейнеров (C2).

## Логика принятия основного решения

#### Контекстная диаграмма (C2) основного решения в нотации С4

[Диаграмма](C2_main.puml)

### 1. Выбор типов БД

**На ферме: TimescaleDB + SQLite**

- **TimescaleDB** — основное хранилище:
    - Гипертаблица для показаний датчиков (миллионы записей, временные ряды)
    - Обычная таблица для пользовательских метрик (тысячи записей, не требуют временнóй агрегации)
    - Поле `synced` для буферизации данных при потере интернета
- **SQLite** — хранилище учётных записей пользователей фермы (отдельный файл, не требует сервера)

### 2. Выбор протоколов взаимодействия

**Решение:** прямое синхронное взаимодействие (HTTP/gRPC) + общая БД.

**Почему:**
- Проще разработка и отладка MVP
- БД обеспечивает сохранность данных и буферизацию (флаг `synced`)
- Время оповещения <5 с достигается прямыми вызовами

### 3. Состав контейнеров на ферме

| Контейнер                    | Технологии              | Ответственность                                                               |
|------------------------------|-------------------------|-------------------------------------------------------------------------------|
| Веб-портал                   | React + Nginx           | UI для оператора и агронома (просмотр, управление, добавление метрик)         |
| Сервис сбора данных          | Python + FastAPI        | Сбор показаний датчиков, приём метрик, управление кормушками, push-оповещения |
| Сервис видеоаналитики        | Python + FastAPI        | RTSP → вызов внешней нейросети, передача тревог                               |
| Сервис управления кормушками | Python + pymodbus       | Приём команд, отправка Modbus                                                 |
| Сервис аутентификации        | Python + PyJWT + SQLite | Локальная аутентификация (offline)                                            |
| Сервис синхронизации         | Python + aiokafka       | Отправка данных с флагом `synced=false` в Kafka                               |
| Локальная БД                 | TimescaleDB + SQLite    | Хранение событий, показаний, метрик, пользователей                            |

### 4. Пользовательские метрики

**Решение:** агроном добавляет метрики через веб-портал → `Сервис сбора данных` сохраняет их в локальную БД (обычная таблица). 

### 5. Синхронизация с головным офисом

**Решение:** `Сервис синхронизации` отправляет в Kafka показания датчиков, события тревог и логи досыпок (данные, нужные для аналитики в офисе).

### 6. Две зоны аутентификации

- **Ферма (offline):** SQLite + JWT (оператор, агроном, ветеринар)
- **Офис (online):** Keycloak + OAuth2 (аналитик, менеджер)

## Риски

| Риск                                               | Мера снижения                                                     |
|----------------------------------------------------|-------------------------------------------------------------------|
| Монолитность сервиса сбора данных                  | feeder_controller выделен; при нагрузке — разделить               |
| SQLite и TimescaleDb без репликации                | Резервное копирование, синхронизация с Keycloak (для SQLite)      |
| Пользовательские метрики не видны в головном офисе | Для MVP достаточно; при необходимости — расширить синхронизацию   |

## Альтернативное решение

#### Контекстная диаграмма (C2) альтернативного решения в нотации С4

[Диаграмма](C2_alternative.puml)

**Использование брокера сообщений RabbitMQ на ферме.** 
В этом варианте все сервисы на ферме общаются через централизованный брокер RabbitMQ. Сервисы не вызывают друг друга напрямую, а публикуют и подписываются на сообщения.

**Как устроено:**

| Компонент                    | Что делает                                                               |
|------------------------------|--------------------------------------------------------------------------|
| Сервис сбора данных          | Принимает показания датчиков, публикует в RabbitMQ                       |
| Сервис видеоаналитики        | Обрабатывает RTSP, вызывает нейросеть, публикует тревоги в RabbitMQ      |
| Сервис управления кормушками | Подписывается на RabbitMQ, получает команды, отправляет Modbus           |
| Сервис оповещений (alerting) | Подписывается на тревоги из RabbitMQ, отправляет WebSocket на веб-портал |
| Сервис синхронизации         | Подписывается на RabbitMQ, отправляет все события в Kafka                |
| RabbitMQ                     | Центральная шина: очереди тревог, показаний, команд                      |
| SQLite                       | БД пользователей (логины, хеши, роли)                                    |

**Что отсутствует в альтернативе:**
- TimescaleDB не используется — RabbitMQ сам хранит сообщения на диске в очередях.
- Сервис оповещений вынесен отдельно (в основном решении он объединён с data_collector).

**Преимущества:**
- Асинхронная связь — сервисы не блокируют друг друга.
- Легко добавить новый сервис — просто подписать его на нужную очередь.
- Встроенная поддержка MQTT для беспроводных датчиков.
- Сообщения сохраняются на диске (не теряются при перезапуске).

**Недостатки и причины отклонения:**

| Недостаток                   | Пояснение                                                                                                                                                                                                                        |
|------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Проблема долгой автономности | RabbitMQ хранит сообщения на диске, но при отключении интернета на 24+ часа объём накопленных данных может стать критическим (особенно видео-тревоги). Очереди не оптимизированы для хранения гигабайтов невычитанных сообщений. |
| Потребление ресурсов         | RabbitMQ требует дополнительной памяти и CPU, а также отдельного дискового пространства под очереди. На edge-сервере фермы каждый ресурс на счету.                                                                               |
| Дополнительная точка отказа  | При падении RabbitMQ вся коммуникация между сервисами останавливается.                                                                                                                                                           |
| Административная нагрузка    | Нужно настраивать очереди, права, пользователей, мониторинг брокера.                                                                                                                                                             |

**Почему эта альтернатива не подходит:**

- Для MVP RabbitMQ создаёт избыточную сложность без явной выгоды.
- Прямые вызовы (HTTP/gRPC) проще в отладке и мониторинге.
- Основное решение использует TimescaleDB с полем `synced` — это и хранилище, и буфер одновременно, без лишних компонентов.
- RabbitMQ не рассчитан на долгосрочное хранение больших объёмов данных при потере связи (24+ часа). Это требует отдельной регламентной чистки очередей или увеличения диска.
- При масштабировании (50+ ферм, 10+ сервисов) возможно рассмотреть переход на эту архитектуру, но не на старте.
